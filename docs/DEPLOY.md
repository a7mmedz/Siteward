# Deploying Siteward

Target (free tiers): **database on Neon**, **API on Render**, **frontend on Vercel**. Both hosts serve
HTTPS only; the API sends HSTS and the frontend config does too. Everything below is done once,
by a person with access to the three accounts. Nothing in this repository contains real secrets.

Total time: about 20 minutes.

```
Browser ──HTTPS──▶ Vercel (static PWA, frontend/)        Render (Express API, backend/) ──TLS──▶ Neon Postgres
        └─────────HTTPS (CORS, Bearer JWT)────────────▶ https://siteward-api.onrender.com/api
```

---

## 0. Before you start

- Push this repository to GitHub (Render and Vercel deploy from it).
- Choose two demo passwords (inspector and supervisor), at least 12 characters. Keep them out of Git.

## 1. Database — Neon

1. Sign in at <https://neon.tech> → **New project** → name `siteward`, Postgres 16, a region close to
   your Render region (e.g. Frankfurt / `eu-central-1`).
2. Open **Connection details**, pick the **pooled: off** (direct) connection string, and copy it. It
   looks like `postgresql://USER:PASSWORD@ep-xxx.eu-central-1.aws.neon.tech/neondb?sslmode=require`.
   Prisma migrations need the direct (non-pooled) URL.

> Alternative: a Render Postgres instance works too (copy its **External Database URL**), but the
> free Render database expires after 30 days; Neon's free tier does not.

## 2. API — Render

1. Sign in at <https://render.com> → **New → Blueprint** → connect the GitHub repository. Render
   reads [`render.yaml`](../render.yaml) and proposes the `siteward-api` web service.
2. Fill the variables Render asks for:

   | Variable | Value |
   |---|---|
   | `DATABASE_URL` | the Neon URL from step 1 |
   | `CORS_ORIGIN` | your Vercel URL, e.g. `https://siteward.vercel.app` (you can fill it after step 3; add preview URLs comma-separated if needed) |
   | `SEED_INSPECTOR_PASSWORD` | your inspector demo password |
   | `SEED_SUPERVISOR_PASSWORD` | your supervisor demo password |

   `JWT_SECRET` is generated by Render. `DEMO_TOOLS=true` enables the supervisor-only failure demo
   (AC8); set it to `false` for any real use.
3. **Apply**. The build runs `npm ci --include=dev && npm run build -w backend`; each start runs
   `prisma migrate deploy` (idempotent) and then the server.
4. Seed the demo data once: service → **Shell** → run

   ```bash
   npm run db:seed -w backend
   ```

   Expected output: `Seeded 2 users, 3 sites, 1 checklist template.` (Safe to re-run; it also
   resets the two demo passwords to the current env values.) No Shell on your plan? Run the same
   command on your machine with `DATABASE_URL`, `SEED_INSPECTOR_PASSWORD` and
   `SEED_SUPERVISOR_PASSWORD` set to the production values.
5. Verify:
   - `https://<your-service>.onrender.com/api/health` → `{"status":"ok","db":"up",…}`
   - `https://<your-service>.onrender.com/api/docs` → Swagger UI

> **Free-tier cold start:** a free Render service sleeps after ~15 minutes without traffic, and the
> first request then takes ~30–60 s. Open `/api/health` a minute before a demo. The app itself keeps
> working meanwhile (it is offline-first): the header shows `Sync failed · Retry` until the API
> wakes, then syncs automatically.

## 3. Frontend — Vercel

1. Sign in at <https://vercel.com> → **Add New → Project** → import the repository.
2. **Root Directory:** `frontend`. Framework is detected as Vite; build settings come from
   [`frontend/vercel.json`](../frontend/vercel.json) (install at the repo root because of npm
   workspaces, build `npm run build`, output `dist`, SPA rewrites, no-cache for `sw.js`). Leave
   "Include files outside the root directory" enabled (the default).
3. **Environment variable** (Production and Preview):

   | Variable | Value |
   |---|---|
   | `VITE_API_URL` | `https://<your-service>.onrender.com/api` |

   The build fails on purpose if this is missing on Vercel.
4. **Deploy**, then copy the production URL into Render's `CORS_ORIGIN` (step 2.2) if you have not
   yet. Render redeploys automatically after an env change.

## 4. Verify the deployment

1. Open the Vercel URL on a phone or in Chrome. Sign in as `inspector@siteward.test` with your
   inspector password. The header shows `Online · Synced` and three sites are listed.
2. Create an inspection, fill a few items, wait for `Online · Synced`; confirm it in Swagger UI with
   `GET /inspections` (Authorize with a token from `POST /auth/login`).
3. Turn on airplane mode, reload: the app opens with your data; edit; reload; turn airplane mode off:
   it syncs (`docs/demo-script.md` has the full walkthrough).
4. Paste both URLs into the README's **Demo and access** section.

## Troubleshooting

| Symptom | Fix |
|---|---|
| Sign-in says "needs a connection" while online | CORS: `CORS_ORIGIN` on Render must exactly match the Vercel origin (scheme + host, no trailing slash). |
| `Sync failed · Retry` right after opening | Render cold start; wait ~1 minute or open `/api/health`. |
| Render build fails at `prisma generate` | Check the root `package.json` `allowScripts` still approves `prisma` and `@prisma/engines`. |
| Migrations fail with a connection error | Use Neon's direct (non-pooled) URL with `sslmode=require`. |
| Users get an old version | Normal for a PWA: the app shows "A new version is ready · Reload". `sw.js` is served with `no-cache`, so it is checked on every visit. |

## Rolling back

Render and Vercel both keep previous deploys: **Rollback** in either dashboard. Migrations are
additive; there is only the `init` migration today.
